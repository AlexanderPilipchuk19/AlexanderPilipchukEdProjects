# Задание 1

20 баллов

Возьмем за основу код, умеющий стартовать на пустой плате `x86`. 

1. Организуем старт

2. Реализуем несколько функций для печати в условиях отсутствия операционной системы

3. Реализуем несколько вспомогательных функций для базового ввода-вывода

В частности, реализуем такие функции:

```
// очищаем экран и делает текущей позицией
// для последующей печати левый верхний угол
void reset();


// выводим строку s, начиная с текущей позиции
// обновляя ее

// если дошли до правой границы экрана, то переходим на следующую строку

// если очередной символ - перевод строки, то досрочно переходим
// на следующую строку

// если в момент перехода на следующую строку находимся в самой нижней строке,
// то прокручиваем строки вверх на одну строку
// (верхняя строка исчезает, остальные - поднимаются)
void puts(const char *s);


// выводим десятичное число, начиная с текущей позиции и обновляя ее
//
// если число неотрицательно, то выводим только значимые цифры
//
// если число отрицательно, то выводим сначала знак -, а после него - значимые цифры
// его абсолютного значения
void putnum(int v);
```

5. Реализуем функцию, искуственно синхронно "засыпающую" примерно на заданное число милисекунд:

- печатаются оба счетчика (обе печатаются из цикла, не из обработчика прерывания)

Если другие задания не делаются, то цикл должен быть бесконечным.


# Задание 2 

50 баллов 

Обработка прерывания от таймера - это важный шаг на пути к операционной системе.

И это то, без чего практически никак не обойтись, если речь идет об ОС, поддерживающей
параллельную работу процессов.

Можно обойтись без работы с внешней памятью, без драйверов устройств, без загрузки новых
процессов во время работы ОС, без организации своего пространства памяти для каждого процесса.

Без всего этого ОС может сильно потерять в практической полезности, но как-то дышать она может.

## Пользовательские процессы

Загружать в память новые пользовательские процессы мы не будем.

Будем запускать в качестве пользовательских процессов функции, которые будут собираться вместе с кодом нашей ОС.

Определимся с типами параметров и возвращаемых значений таких функций.

Возвращаемый тип пусть будет `int` - чтобы отражать статус завершения (`0` - успех, не `0` - код ошибки)

А параметров пусть будет `2`:

- контекст

- количество аргументов

- аргументы

Контекст - это структура `struct context`, описывающая связь пользовательского процесса с системой. Конкретные поля определим чуть позже.

Аргументы - массив строк - аналог аргументов командной строки.

В итоге функция с кодом пользовательского процесса будет выглядеть так:

```
int p(struct context* ctx, int argc, char **args) {
  // ...
  return 0;
}

```

## Задание начального списка пользовательских процессов

Определим массив указателей на функции с кодом пользовательских процессов.

В нем будем хранить адреса функций, которые хотим запустить как пользовательские процессы:

```
int(* processes[])(struct context* ctx, int argc, char **args) = {
  &some_process,
  &another_process,
  &another_process,
  0,
};
```

Указатели могут повторяться. Это нормально. Просто мы запустим два пользовательских процесса, исполняющих один код.

0 в конце нужен, чтобы понять, что перечень пользовательских процессов закончен.

## Запуск пользовательских процессов

Наша ОС должна пройтись по перечню пользовательских процессов и запустить их по очереди.

На каждый пользовательский процесс нужно выделить память под стек вызовов и под контекст - не тот, который `struct context`,
а тот, который состояние регистров.

Можно рассчитывать на то, что стек вызовов не будет очень глубоким. 20 вызовов, не больше.

И в нашей ОС не будут создаваться новые пользовательские процессы, кроме тех, что заданы в переменной `processes`.


## Кооперативная и конкурентная модели параллелизма

Кооперативная модель параллелизма предполагает, что каждый участник добровольно отдает другим участникам возможность исполняться.
(Обычно в тот момент, когда ему нужно чего-то ждать).

Конкурентная модель параллелизма предполагает, что возможность исполняться отбирается у процесса и передается другому по истечении
какого-то времени.

Мы реализуем смешанную модель.

### Кооперативная часть

Запущенные при старте пользоветельские процессы должны работать по кооперативной модели.

Первым начинает работать заданный первым пользовательский процесс.

Когда первый запущенный пользовательский процесс вызывает функцию `yield()`, управление передается следующему
пользовательскому процессу. И так по кругу.

В рамках этого задания считаем, что ни один пользовательский процесс не завершается.

Если какой-то из пользовательских процессов крутится в бесконечном цикле и не вызывает `yield()` - ни один другой из запущенных
пользовательских процессов работать не должен.

### Конкурентная часть

У нас будет системный процесс, отвечающий за печать. Он будет работать всегда.

И после k-го тика после начала работы пользовательских процессора будет происходить переключение контекста на системный процесс.

Можно это понимать так, что работают два процесса - системный и один обобщенный пользовательский, включающий в себя то, что определено
в переменной `processes`..

Пользовательский внутри себя делит свое время между своими единицами параллелизма кооперативным способом.

Переключение с пользовательского на системный происходит конкурентным образом.

А в обратную сторону - нет. Потому что, все, что нужно делать системному процесс - это напечатать текущее состояние пользовательских.
Это делается быстро и нет смысла делать это снова, пока у пользовательских процессов не было возможности еще поработать.


## Упрощающие допущения

Предполагаем, что все процессы работают бесконечно.

Это позволит обойтись без обработки завершения процесса.

## Частные случаи

Если пользовательских процессов нет - системный просто крутится в холостом цикле. Переключений контекста не происходит.

Если пользовательский процесс один, то его `yield` приводит к тому, что управление передается системному, а после `yield` в системном снова
продолжает работать пользовательский.

Если пользовательский процесс не один, то его `yield` приводит к тому, что управление передается следующему пользовательскому и до следующего
конкурентного переключения контекстов продолжают работать пользовательские (переключаясь на каждом `yield`-е на следующий по кругу).

## Печать

Печать - ответственность системного процесса.

Добавим в `struct context` поле `int state`. Каждый процесс его может менять, чтобы отражать в нем свой прогресс. Это может быть результат
вычисления или счетчик прогресса.

Что бы пользовательский процесс туда ни написал - системный должен это печатать.

Печататься это должно так:

* в левом верхенем углу печатаем #<номер печати>, где <номер печати> - число, равное порядковому номеру исполнения логики печати, начиная с 0

* пропускаем строку

* печатаем p#<номер пользовательского процесса>: <значение state> для каждого процесса

Пусть нумерация начинается с 0 и на каждую строку влезает по 4 процесса, и вывод начинается на колонках 0, 20, 40, 60. 

Например, если запущено 6 пользовательских процессов, то верхняя часть должна выглядеть как-то так:

```
#43242

p0: 3342            p1: 43423       p2: 15              p3: -342
p4: 555555          p5: 423432
```

# Задание 3

30 баллов

Поддержим аккуратное заверщение пользовательских процессов.

Любой пользовательский процесс может завершиться, исполнив `return` с указанием возвращаемого значения.

В этом случае:

- контекст передает так, как будто это был вызов `yield`

- логика переключений контекстов продолжает работать так, как будто завершившегося процесса никогда не было

- системный процесс вместо значения `state` выводит для завершившегося процесса возвращенное значение

Также в выводе системного процесса появляется еще один раздел.

После последней строки с состояними процессов идет пустая строка, после которой - `Finished: ` и перечень номеров завершенных процессов
через запятую.
