## Что реализовано

Была реализована программная модель системы «процессор-кэш-память» для архитектуры RISC-V, поддерживающая исполнение команд RV32I и RV32M,  чтение начального состояния из бинарного файла, сохранение выходного состояния памяти и вывод статистики кэша для двух политик вытеснения: `LRU` и `bit-pLRU`. Формат запуска задаётся аргументами `-i <input>` и `-o <output> <address> <size>`. В поток `stdout` печатается таблица с общим `hit_rate`, а также отдельными значениями `instr_hit_rate` и `data_hit_rate`.

## Описание

### Полученные параметры системы

| **Параметр**         | **Значение**            |
| -------------------- | ----------------------- |
| **MEMORY_SIZE**      | 262144 байт (256 Кбайт) |
| **ADDRESS_LEN**      | 18 бит                  |
| **CACHE_TAG_LEN**    | 8 бит                   |
| **CACHE_INDEX_LEN**  | 5 бит                   |
| **CACHE_OFFSET_LEN** | 5 бит                   |
| **CACHE_SIZE**       | 4096 байт (4 Кбайт)     |
| **CACHE_LINE_SIZE**  | 32 байта                |
| **CACHE_LINE_COUNT** | 128                     |
| **CACHE_SET_COUNT**  | 32                      |
| **CACHE_WAY**        | 4                       |

- Смещение (Offset):
    
    Размер кэш-линии составляет 32 байта. Для адресации байта внутри линии необходимо:
    
    $$CACHE\_OFFSET\_LEN = \log_2(32) = 5 \text{ бит}$$
    
- Индекс (Index):
    
    Количество наборов вычисляется как отношение общего количества линий к ассоциативности:
    
    $$CACHE\_SET\_COUNT = \frac{CACHE\_LINE\_COUNT}{CACHE\_WAY} = \frac{128}{4} = 32$$
    
    Для адресации набора необходимо:
    
    $$CACHE\_INDEX\_LEN = \log_2(32) = 5 \text{ бит}$$
    
- Тэг (Tag):
    
    Согласно варианту и коду программы, длина тэга составляет 8 бит.
    
    $$CACHE\_TAG\_LEN = 8 \text{ бит}$$
    
- Длина адреса (Address Length):
    
    Полная длина физического адреса складывается из длин тэга, индекса и смещения:
    
    $$ADDRESS\_LEN = Tag + Index + Offset = 8 + 5 + 5 = 18 \text{ бит}$$
    
    
    
- Размер кэша (Cache Size):
    
    Полезный объем данных кэша:
    
    $$CACHE\_SIZE = SetCount \times Way \times LineSize = 32 \times 4 \times 32 = 4096 \text{ байт}$$



## Реализация
## Memory
Класс `Memory` моделирует оперативную память фиксированного размера `MEMORY_SIZE`. Внутри он хранит два массива одинаковой длины: массив байтов `data`, содержащий собственно значения памяти, и массив логических флагов `initialized`, показывающий, был ли соответствующий байт загружен из входного файла или записан в ходе исполнения программы. При создании объекта оба массива полностью обнуляются: память заполняется нулями, а все байты помечаются как неинициализированные.

Загрузка содержимого памяти выполняется методом `loadFragments`. На вход ему передаётся список фрагментов, считанных из `task.bin` или другого входного бинарного файла. Для каждого такого фрагмента проверяется, что диапазон `address ... address + size - 1` не выходит за пределы `MEMORY_SIZE`; после этого байты копируются в массив `data`, а соответствующие элементы массива `initialized` устанавливаются в `true`.

Чтение из памяти реализовано методами `read8`, `read16` и `read32`, а запись — методами `write8`, `write16` и `write32`. Все эти методы сначала проверяют корректность адресации, то есть не допускают выхода за пределы массива памяти. Для многобайтовых операций используется порядок : младший байт слова хранится по меньшему адресу, а старшие — по последующим адресам.

При сохранении выходного состояния программа сначала выполняет `flush` кэша, а уже потом выгружает массив `memory.getData()` в выходной файл.
### 4.1. `Memory`

Класс `Memory` реализует байтовую модель оперативной памяти. Внутри хранится массив `data[MEMORY_SIZE]` и массив `initialized[MEMORY_SIZE]`. Первый содержит сами байты памяти, второй помечает, какие байты были загружены или записаны. Конструктор заполняет память нулями и очищает флаги инициализации. Загрузка исходного состояния производится методом `loadFragments`, который получает список фрагментов из входного файла и копирует их в нужные адреса. Для работы ISA реализованы методы `read8`, `read16`, `read32`, `write8`, `write16`, `write32`. Также предусмотрена проверка выхода за пределы допустимого адресного пространства. 

### 4.2. `CPU`

Класс `CPU` хранит состояние процессора: программный счётчик `pc` и массив из 32 регистров `regs`. Регистр `x0` ведёт себя в соответствии с архитектурой RISC-V: при чтении всегда возвращает ноль, при записи не изменяется. Метод `loadState` загружает начальные значения `pc` и регистров `x1..x31` из входного файла, а `saveState` сохраняет их для выходного файла. Доступ к регистрам организован через методы `getReg` и `setReg`.

### 4.3. `Decoder`

Класс `Decoder` отвечает за декодирование 32-битного машинного слова в структуру `DecodedInstruction`. Для этого из инструкции выделяются поля `opcode`, `rd`, `rs1`, `rs2`, `funct3`, `funct7`, после чего определяется тип инструкции. В декодере поддерживаются инструкции арифметики, логики, сдвигов, сравнений, переходов, работы с памятью, а также команды расширения `M`: `mul`, `mulh`, `mulhsu`, `mulhu`, `div`, `divu`, `rem`, `remu`. Непосредственные операнды восстанавливаются отдельным методом `signExtend`, который выполняет знаковое расширение до 32 бит. Отдельно декодируются форматы `I`, `S`, `B`, `U` и `J`.

### 4.4. `Executor`

Класс `Executor` исполняет все инструкции, которые не относятся к загрузке и записи через кэш. В нём реализованы операции `ADD`, `SUB`, `ADDI`, логические операции, сдвиги, сравнения, ветвления `BEQ/BNE/BLT/BGE/BLTU/BGEU`, переходы `JAL/JALR`, а также инструкции расширения `M`. Для деления и остатка предусмотрены все специальные случаи, предусмотренные ISA: деление на ноль и случай переполнения `INT_MIN / -1`. Исполнение организовано через статический метод `execute`, который получает уже декодированную инструкцию, текущее состояние процессора и объект памяти. После выполнения инструкция либо изменяет регистры и `pc`, либо возвращает `false`, если встретилась `ECALL`, `EBREAK` или неизвестная команда.

## 5. Формат входного и выходного файла

Чтение входного файла выполняется функцией `readInputFile`. Сначала она считывает начальный `pc`, затем 31 значение регистров `x1..x31`, а после этого — произвольное число фрагментов памяти. Каждый фрагмент задаётся тройкой: начальный адрес, размер и сам массив байт. Именно такой формат задан в условии лабораторной. Запись выходного файла выполняется функцией `writeOutputFile`: в файл сохраняются текущий `pc`, регистры `x1..x31`, затем адрес и размер выгружаемого фрагмента, после чего записывается соответствующий диапазон байтов из оперативной памяти. Таким образом, выходной файл отражает именно то состояние памяти, которое видит исполняемая программа после завершения эмуляции.

## 6. Организация кэша
Логика кэша реализована в абстрактном классе `Cache`. Для каждой строки хранятся признак валидности, признак модификации, tag и массив байтов строки. Метод `parseAddress` разбивает адрес на `tag`, `index` и `offset`. Метод `loadLine` загружает 32-байтную строку из оперативной памяти, а `evictLine` при необходимости записывает dirty-строку назад в память.

Метод `read(address, size, is_instruction)` учитывает обращение либо как инструкционное, либо как обращение к данным. Если строка уже находится в соответствующем множестве, происходит `hit`; иначе выбирается жертва, при необходимости вытесняется старая строка, загружается новая и затем обновляется состояние политики вытеснения. Аналогично, метод `write` реализует запись с политикой `write-allocate`: при промахе строка сначала подгружается в кэш, затем модифицируется и помечается как dirty.

### 6.1. Общая структура

Кэш реализован абстрактным классом `Cache`. Внутри него хранится двумерный массив `lines[CACHE_SET_COUNT][CACHE_WAY]`, то есть для каждого из 32 наборов имеется по 4 строки. Каждая строка представлена структурой `CacheLine`, содержащей:
- `valid` — признак того, что строка занята;
- `dirty` — признак того, что строка была изменена и должна быть записана обратно в память при вытеснении;
- `tag` — тег адреса;
- `data[CACHE_LINE_SIZE]` — байты строки;
- `maxused` — служебный бит для реализации битовой псевдо-LRU.

### 6.2. Разбор адреса

Для обращения к кэшу адрес разбивается на три части: `offset`, `index` и `tag`. Это делает метод `parseAddress`: младшие 5 бит задают смещение внутри строки, следующие 5 бит — индекс набора, а старшие 8 бит — тег. Благодаря такому разбиению любой физический адрес однозначно отображается в конкретный набор и конкретное смещение внутри кэш-линии.

### 6.3. Чтение

Метод `read(address, size, is_instruction)` моделирует одно обращение к кэшу. Сначала увеличиваются счётчики статистики: отдельно для инструкций и для данных. Затем в нужном наборе перебираются все четыре строки и ищется строка с совпадающим тегом и установленным `valid`. Если совпадение найдено, фиксируется попадание, обновляется состояние политики вытеснения и из массива `data` извлекается требуемое число байт. Если совпадения нет, выбирается жертва с помощью виртуального метода `selectVictim`, при необходимости вытесняемая строка записывается обратно в память методом `evictLine`, после чего в кэш загружается нужная строка методом `loadLine`. После этого политика вытеснения также обновляется. 

### 6.4. Запись

Метод `write(address, value, size)` реализует политики `write-back` и `write-allocate`. Это означает следующее. Если запись попадает в уже имеющуюся кэш-строку, байты меняются только в кэше, а строка помечается как `dirty`. Если записи соответствующей строки в кэше нет, сначала эта строка загружается из памяти, и только затем в неё вносятся изменения. В оперативную память данные уходят не сразу, а только при вытеснении строки или при полном сбросе кэша через `flush`.

## 7. Политики вытеснения

### 7.1. `LRU`

Класс `CacheLRU` реализует точную политику `Least Recently Used`. Для каждой строки кэша хранится отметка времени последнего использования в массиве `access_time[set][way]`, а глобальный счётчик `global_time` увеличивается после каждого обращения. При выборе жертвы метод `selectVictim` сначала пытается найти невалидную строку, а если все строки заняты, выбирает строку с минимальной отметкой времени, то есть строку, к которой обращались раньше всего. Метод `updateReplacement` просто записывает текущее значение `global_time` в соответствующую ячейку и затем увеличивает счётчик.

### 7.2. `bit-pLRU`

Класс `CacheBitPseudoLRU` реализует битовую псевдо-LRU. В данной реализации для каждой строки хранится булев флаг `maxused`, который показывает, была ли эта строка использована в текущем цикле наблюдения. После обращения к строке её флаг устанавливается в `true`. Если в наборе все четыре строки оказываются помеченными как использованные, все биты сбрасываются в `false`, и только у только что использованной строки флаг снова устанавливается в `true`. При выборе жертвы сначала ищется невалидная строка, а если набор заполнен, выбирается первая строка, у которой `maxused == false` то есть ищется первая строка, которая в текущем цикле ещё не была помечена как недавно использованная. Таким образом, алгоритм не хранит точный порядок обращений, как LRU, но старается избегать вытеснения недавно использованных строк.

## 8. Класс `Emulator` и жизненный цикл моделирования

Класс `Emulator` объединяет все остальные компоненты: `CPU`, `Memory`, `Decoder`, а также два независимых экземпляра кэша — `cache_lru` и `cache_bplru`. При запуске `loadInput` загружает начальные значения процессора и памяти, а в `return_address` сохраняется начальное значение регистра `x1`, то есть `ra`. Именно достижение этого адреса считается нормальным завершением программы по условию. Основной цикл расположен в методе `run`. На каждой итерации он:
1. берёт текущий `pc`;
2. завершает работу, если `pc == return_address`;
3. извлекает инструкцию через `fetchInstruction(pc)`;
4. декодирует её;
5. либо выполняет загрузку/запись через кэш, либо передаёт управление `Executor::execute`.

Выборка инструкции и доступы к данным делаются сразу через оба кэша. Для состояния процессора используется результат чтения из LRU-кэша, а вызовы второго кэша нужны для того, чтобы на тех же самых обращениях получить независимую статистику для `bpLRU`. То есть обе политики сравниваются на совершенно одинаковой последовательности запросов. Перед сохранением результата вызывается `flush` у обоих кэшей, чтобы все «грязные» строки были выгружены в оперативную память. После этого сохраняются регистры, `pc` и нужный диапазон памяти. 



## 9. Как формируется `task.bin`

В `generate_task.py` вручную кодируются инструкции RISC-V через функции `encode_r_type`, `encode_i_type`, `encode_s_type`, `encode_b_type`, `encode_u_type`, `encode_j_type`, после чего собирается массив машинных слов `instructions`. Затем скрипт создаёт `task.bin` в том же формате, который ожидает эмулятор: сначала записывается начальный `pc`, затем 31 регистр, затем фрагмент кода, а затем фрагмент данных. В скрипте задаются `code_start = 0x20000`, `pc = 0x20000`, `ra = 0`, а область данных начинается с `data_start = 0x1000` и имеет размер `0x4000` байт.

Таким образом, `task.bin` содержит:

- начальный `pc = 0x20000`;
    
- регистры `x1..x31`, в данном тесте заполненные нулями, поэтому стартовое значение `ra` равно 0;
    
- фрагмент кода длиной `23 * 4 = 92` байта;
    
- фрагмент данных размером `0x4000 = 16384` байт, заполненный нулями.

## 10. Как подбирался тест под нужные проценты попаданий

По условию требовалось добиться хотя бы одного вытеснения из кэша и получить заданные проценты попаданий хотя бы для одной политики. В моём варианте целевые значения были: `hit% (instr) = 95.2381%` и `hit% (data) = 37.5000%`.

### 10.1. Почему данные дают `37.5000%`

В `task.asm` присутствует ровно 8 инструкций `lw`. Последовательность адресов, к которым они обращаются, такова:

- `0x1200`
    
- `0x1600`
    
- `0x1A00`
    
- `0x1E00`
    
- `0x1200`
    
- `0x1600`
    
- `0x1A00`
    
- `0x2200`
    

Размер строки кэша равен 32 байта, а число множеств равно 32, поэтому шаг `0x400 = 1024` байта специально выбран равным `32 * 32`. Это означает, что при прибавлении `0x400` меняется tag, но не меняется индекс множества. Следовательно, все перечисленные адреса попадают в одно и то же множество кэша, но соответствуют разным строкам памяти.

Первые четыре загрузки заносят в одно множество четыре разные строки. После этого множество полностью заполнено. Следующие три обращения идут к уже загруженным строкам и поэтому дают три попадания. Последнее обращение идёт к пятой уникальной строке того же множества (`0x2200`), из-за чего возникает промах и как минимум одно вытеснение. Итого получается:

- 8 обращений к данным;
    
- 3 попадания;
    
- 5 промахов;
    
- `data_hit_rate = 3 / 8 * 100% = 37.5000%`.
    

### 10.2. Почему инструкции дают `95.2381%`

Код теста содержит 23 инструкции, каждая длиной 4 байта, то есть общий размер кода равен 92 байта. При размере строки 32 байта этот код занимает ровно 3 кэш-линии инструкций: первые 8 инструкций лежат в первой строке, следующие 8 — во второй, оставшиеся 7 — в третьей.

Динамически программа выполняется так:

- первые 20 инструкций выполняются по одному разу;
    
- затем короткая петля из двух инструкций (`addi t0, t0, -1` и `bne t0, zero, loop`) выполняется 21 раз;
    
- затем один раз выполняется `jalr zero, 0(ra)`.
    

Отсюда общее число выборок инструкций равно:

- `20 + 2 * 21 + 1 = 63`.
    

Промахи по инструкциям здесь только обязательные: по одному при первом входе в каждую из трёх строк кода. После того как третья строка загружена, вся короткая петля целиком находится внутри уже присутствующей кэш-линии и выполняется без новых инструкционных промахов. Поэтому:

- `instr_access = 63`;
    
- `instr_miss = 3`;
    
- `instr_hit = 60`;
    
- `instr_hit_rate = 60 / 63 * 100% = 95.2381%`.
    


# Что было не так с первой попыткой 
В первой версии при выполнении операции записи в кэш отсутствовал механизм вытеснения грязных строк, если происходил промах (miss), т е если программа пыталась записать данные по адресу, которого нет в кэше, старая версия могла просто перезаписать существующую строку, не сохранив измененные грязные данные обратно в основную память. Это приводило к потере данных. 
**Что исправлено:**  добавлена проверка: если при записи происходит промах, сначала выбирается жертва (victim), вызывается `evictLine` (которая сохраняет данные в память, если они были изменены), и только потом загружается новая строка.

В начальной версии функции декодирования и выполнения некоторых инструкций (`ADDI`, `LW`, `LH` и тп) неправильно обрабатывали отрицательные смещения и константы, а RISC-V использует знаковое расширение для 12-битных и 20-битных констант. Если число было отрицательным, старая программа могла интерпретировать его как огромное положительное число, из-за чего переходы осуществлялись не туда, а адреса памяти вычислялись неверно.
**Что исправлено:**  улучшена функция `signExtend` и логика сборки `imm` для инструкций типа I, B и J, обеспечивая корректное преобразование битовых полей в знаковые 32-битные целые числа.

Также в первой версии реализация алгоритмов замещения строк в кэше (LRU pLRU) содержала логические ошибки в обновлении счетчиков и битов состояния: кэш выбирал для удаления не ту строку, которая использовалась реже всего. Это приводило к аномально низкому проценту попаданий и не соответствовало ожидаемому поведению реального процессора.

**Что исправлено:** Переписана логика `updateReplacement` и `selectVictim` для обоих алгоритмов, чтобы корректно отслеживать историю доступа к каждой строке в наборе.

**Инструкция `AUIPC`:** В первой версии к PC прибавлялось значение, не сдвинутое на 12 бит влево, или само смещение вычислялось неверно. В исправленной версии `AUIPC` корректно формирует адрес, добавляя смещение к текущему PC.

**Инструкции загрузки/сохранения (`LB`, `LH`, `SB`, `SH`):** Были уточнены маски для работы с байтами и полусловами, чтобы при загрузке `LB` (Load Byte) правильно происходило знаковое расширение считанного байта до 32 бит.

Добавлены проверки на деление на ноль и более точное приведение типов при вычислении процентов, чтобы в отчете не выводились значения `nan%` там, где данные были доступны.

# Исправление pLRU
В первоначальной реализации pLRU состояние множества хранилось в виде дерева из трёх управляющих битов, по которым выбиралась линия на вытеснение и которые обновлялись после каждого обращения к кэшу. После исправления политика pLRU была реализована через индивидуальные биты недавнего использования maxused у каждой линии множества. Теперь при обращении линия помечается как недавно использованная, а при выборе жертвы предпочтение отдаётся линии, которая не использовалась в текущем цикле обращений. Если все линии множества уже были отмечены как недавно использованные, их флаги сбрасываются, и текущая линия помечается снова. Таким образом, логика вытеснения стала определяться не обходом дерева битов, а явным учётом факта недавнего использования каждой кэш-линии.
